A record of how this project was built and why it is shaped the way it is. The changelog says what shipped and when; this says what the work was actually like. The postmortem takes apart the things that went wrong.

The brief

Write a Prolog interpreter in C. Nothing more specific than that — no target dialect, no performance goal, no deadline. Everything below is a consequence of choices made against a blank sheet, which is worth remembering when reading the parts that went badly.

Day one — the interpreter

The one decision that shaped everything

The first real choice was between compiling clauses to an abstract machine — a WAM, which is what serious systems do — and copying the clause structure at every call. Structure copying was chosen, and the whole design follows from it:

  • Calling a predicate copies its clause onto the heap. That is where the time goes, and it is the factor of a few this interpreter gives away against SWI.
  • Because there is no compiled code, there is no code area, no register allocation and no instruction set to get right. src/machine.c is 636 lines.
  • The continuation is an explicit list of goal frames rather than the C stack, so ancestor/2 on a deep tree costs heap, not a segfault.
  • Cut is not a special instruction. It is an integer — the height the choice point stack must be cut back to — carried in every goal frame. If-then-else, negation, soft cut and catch/3 are then all assembled from that one mechanism plus a kind tag on the choice point.

The cost of the decision is visible in the measurements: about 14.6M inferences a second on nrev, which is respectable for a tree walker and slow for a compiler. The benefit is that the engine can be read in an afternoon, which was worth more here than the speed.

Memory, and the part that was hardest

Three regions, deliberately:

  • a chunked heap that choice points mark and backtracking rewinds, which is free and handles everything a backtracking program produces;
  • arenas for things that must outlive backtracking — clauses, exception balls, findall/3 buffers;
  • plain malloc for the atom table, the choice point stack and the trail.

That covers everything except one case: a deterministic recursion, which allocates and never backtracks, so nothing ever releases. A copying collector was added for exactly that case. The published measurements are the two ends of it: two million iterations of a deterministic recursion peak at 967 MB with the collector disabled, and five million peak at 25 MB with it running.

The collector has one hard restriction — it only runs when the choice point stack is empty — because heap marks are positions in an allocation order that a copying collector destroys. That restriction is the single biggest limitation in the design, and it is on the roadmap under Collecting while choice points are live, where it is honestly labelled as most of the way to a WAM.

Failure-driven loops were a separate problem with a separate answer. A loop over a recursive generator costs about a kilobyte an iteration, because each iteration's choice point pins the heap above it. between/3 and repeat/0 instead retry one choice point in place, keeping their state in the frame, so a million iterations peak at 2.8 MB rather than 754 MB. That is a real asymmetry between the two ways of writing the same loop, and rather than hide it the reference documents it with both numbers.

Documentation as a build product

The reference and the internals document are generated by Python in tools/, not written by hand. tools/docpage.py owns the escaping, the block builders, the design tokens and the page shell; each page has its own generator. Two things follow, and both turned out to matter more than expected:

  • Every predicate signature and every transcript in the reference was checked against the running interpreter, because it was cheaper to run the query than to remember the answer.
  • CI regenerates docs/ and fails if anything changed, so the published pages cannot drift from their generators — a page edited by hand, or a generator changed without rebuilding, fails the build rather than shipping.

CI, and what it immediately found

Adding a build matrix — Linux and macOS, clang and gcc, warnings as errors, sanitizers on every leg — was the roadmap's first item. It found three genuine bugs on its first run, none of which reproduced on the development machine: a POSIX function used under -std=c99 that silently truncated a pointer on Linux, seventeen gcc warnings clang had never mentioned, and an undefined shift that had been quietly producing the right answer. The postmortem goes into all three.

The lesson was cheap to learn and is now permanent: the matrix is not there to prove the code works on other people's machines. It is there because a single compiler on a single platform is a single opinion.

Day two — teaching the thing

Four tutorial levels were written for a reader who had never used Prolog seriously, which turned out to be a much better test of the interpreter than writing more tests would have been.

The method

The same loop every time:

  1. Write the page.
  2. Run every query in it against the real interpreter.
  3. When the page and the interpreter disagree, work out which one is wrong.

Step 3 is the whole value. It caught the page being wrong (a claim that sibling/2 gives two answers when it gives four; a filter described as deterministic when its guarded clauses leave a choice point) and it caught the interpreter being wrong (a stray full stop printed when enumeration was stopped early; max_arity).

Transcripts are captured by driving the toplevel over a pty rather than a pipe, because a pipe does not reproduce the ; prompts or the difference between an answer that ends in a full stop and one that leaves a choice point open. That distinction is pedagogically important — half of the Level 3 material about the cut is about exactly that full stop — so the transcripts have to show it honestly.

What each level cost

  • Levels 1 and 2 (facts and rules; lists and aggregation) were mostly writing. The interpreter behaved.
  • Level 3 (negation, the cut, op/3, DCGs) needed a figure for the cut, and drawing it forced the question of what the cut actually discards. The answer — the remaining clauses of this predicate, plus the alternatives left by goals to the left of it in this body, and nothing older — is exactly what the engine stores as one integer, so the figure and the implementation ended up being the same picture.
  • Level 4 (exceptions, the database, I/O) was the expensive one, because it is where a tutorial stops asking questions and starts changing things. Two undocumented deviations fell out of writing it, and one of them announced itself by hanging: a transcript query that asserted to the predicate it was backtracking through looped forever. That is not a bug — it is the absence of ISO's logical update view — but nothing had said so anywhere.

Housekeeping the tutorials forced

  • make tutorials loads each tutorial program and runs a query from its page. Nothing had been checking that these files still worked.
  • Three defects in the shared page shell surfaced only because the pages were rendered and looked at, not just generated. A CSS escape mangled by Python's octal escapes, note titles overlapping their own text, and *emphasis* reaching six pages as literal asterisks. All three had been live since the site went up.

Day three — a way in, and a green light that was still talking

Nothing about the interpreter changed today. The work was about what a reader arrives to, which is a different problem and had been left undone.

The records needed a keeper

The four records have been at the top of the tree since the first commit, and nothing said so. That is fine while the only person opening the repository is the one who wrote it. It stops being fine the moment anybody else arrives, because the obvious guess is wrong here: docs/ looks like where the documents live, and it is not. It holds generated HTML, built from the Markdown at the root by tools/gen_*.py. Someone who edits a file in docs/ loses the work at the next make doc and finds out only if they look.

CLAUDE.md now says that, along with what each record collects and the rule worth more than the rest of it: every record opens with a note stating its own job, and that note decides what belongs in it. The gloss is deliberately thin, because a summary rots while the document it summarises stays right.

The ledger that was already whole

A convention for laying out projects like this one asks for five records, the fifth being a COMPLETED.md that holds what was built, opposite the roadmap's what is left. This project has four, and adding the fifth would have been the easy thing to do.

It would also have been wrong. ROADMAP.md has said since it was written that finished work moves to The changelog, and the changelog is written that way — its max_arity entry is not a line announcing a release, it is the whole account of what was wrong and what fixed it, with the hash to read it by. The role is filled. A COMPLETED.md beside it would have produced two documents that both look authoritative and disagree inside a month.

The cost of separating them later, if that is ever wanted, is now measured: four inbound links to CHANGELOG.md across the Markdown, and eighteen references to record filenames inside tools/*.py, where each generator carries a map rewriting links between records into site URLs. Renaming a record here is not a rename; it is a rename and a generator change.

Green is not the same as quiet

CI passed on the day's first commit — four jobs, twenty-eight seconds, the documentation-in-sync check among them. It also hung the same annotation on every one of those jobs: actions/checkout@v4 targets Node.js 20, which the runners no longer provide, so each job was being forced onto Node.js 24.

Nothing was broken, and nothing would have been until the forcing turns into a refusal. The bump to @v5 was two lines and safe to make without reading the release notes, because this workflow passes the action no inputs at all; the only difference is the runtime the action itself runs on.

The lesson is small and worth the paragraph anyway. The annotation was visible only because the run was opened and read, rather than glanced at as a green badge — and the badge had been green, carrying this, for some time. What a check reports is not the same as whether it passed.

How the work is checked

The standing discipline, in the order the checks run:

CheckWhat it is for
make checkThe suite, twice: normally and with the collector forced every 1024 inferences.
make test-asanThe suite again under the address and undefined behaviour sanitizers, aborting on UB rather than printing it.
make examplesThe five example programs still produce their answers.
make tutorialsThe four tutorial programs still load and answer.
make doc + git diff --exit-codeThe published pages match their generators.
The matrixLinux and macOS, clang and gcc, -Werror.

Every one of these was added in response to something it would have caught.

Where it stands

About 6,600 lines of hand-written C, 616 lines of library written in Prolog, a 256-test suite, five examples, four tutorial levels, and a reference and internals document generated from the interpreter's own tables.

What it is not: fast, modular, tabled, constrained, or capable of integers larger than 64 bits. Those are on the roadmap or under Not planned, and the reference lists every deviation from ISO it knows about — a list that got two entries longer the week the tutorials were written, which is the honest summary of what writing documentation does for a project.
